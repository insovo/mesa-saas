如果你是为了做**「Kimi + TextIn + JEV」简历筛选系统**，我建议不要只抽取“姓名、学历、工作经历”这种基础字段，而是把简历信息设计成 **结构化原始信息 + 可计算的候选人特征 + 与 JD 匹配所需的信息** 三层。

### 1. 基础身份信息

| 类别   | 建议字段                  |
| ---- | --------------------- |
| 姓名   | 姓名                    |
| 联系方式 | 手机、邮箱                 |
| 地区   | 当前城市、意向工作城市           |
| 求职状态 | 在职/离职/应届              |
| 求职意向 | 目标岗位、目标职能             |
| 工作性质 | 全职/实习/兼职              |
| 期望   | 期望薪资、到岗时间             |
| 其他   | 个人主页、GitHub、LinkedIn等 |

> **身份证号、家庭住址等不建议作为筛选字段。**

# 11. 最重要：从简历中进一步「计算」出来的信息

这部分其实比单纯抽取简历字段更有价值。

例如原始简历只有：

> 2021–2024 XXX汽车有限公司 海外产品质量工程师

系统可以进一步计算：

```text
总工作年限：5.2年
相关工作年限：3.4年
海外相关经验：2.8年
汽车行业经验：5.2年
质量相关经验：3.4年
管理经验：1.5年
海外项目经验：2.8年
```

再进一步形成：

### 候选人能力标签

```text
海外业务
产品质量
项目管理
汽车行业
欧洲市场
认证
供应商管理
英语
跨部门协作
```

### 技能熟练度

例如：

```json
{
  "英语": {
    "level": "熟练",
    "evidence": [
      "雅思7.0",
      "海外工作2年",
      "负责欧洲客户"
    ]
  },
  "项目管理": {
    "level": "较强",
    "evidence": [
      "PMP",
      "负责XX项目"
    ]
  }
}
```

这一步非常适合交给 **JEV/LLM** 做。

# 12. 最后再做「JD匹配特征」

不要让 TextIn 直接判断“是否适合岗位”。

建议 TextIn 只负责：

> **把简历变成可靠的结构化事实。**

然后 Kimi/JEV 根据 JD 做：

```text
硬性条件
├── 学历
├── 专业
├── 工作年限
├── 行业经验
├── 必备技能
├── 语言
└── 地区/到岗要求

核心能力
├── 岗位专业能力
├── 项目经验
├── 行业经验
├── 管理能力
└── 海外经验

加分项
├── 名校
├── 大厂
├── 头部项目
├── 专利/论文
├── 语言
└── 国际经验

风险/疑点
├── 工作频繁跳槽
├── 时间线冲突
├── 经历描述过于模糊
├── 技能缺乏证据
└── JD关键要求未找到证据
```

最终生成类似：

```json
{
  "candidate_id": "C001",

  "hard_match": {
    "education": true,
    "major": true,
    "experience_years": true,
    "industry": true,
    "location": false
  },

  "capabilities": [
    "海外产品质量",
    "项目管理",
    "欧洲认证",
    "供应商管理"
  ],

  "evidence": [
    "负责XX车型欧洲市场质量管理3年",
    "参与XX认证项目",
    "英语可作为工作语言"
  ],

  "gaps": [
    "缺少智能座舱相关经验"
  ],

  "risk_points": [],

  "match_score": 86
}
```

## 如果是你现在这个招聘 SaaS，我建议最终采用这套结构

**TextIn：负责「看懂文件」**

> PDF / DOC / DOCX → OCR/版面解析 → 简历文本 + 基础结构

↓

**Kimi：负责「结构化」**

> 简历文本 → 教育/工作/项目/技能/证书/时间线等 JSON

↓

**JEV：负责「判断」**

> JD + 候选人 JSON → 硬性条件核验 + 能力匹配 + 证据 + 缺口 + 风险 + 面试问题

↓

**你的 SaaS：负责「招聘流程」**

> 批量上传 → 去重 → 自动解析 → 初筛 → 分类 → 排序/分组 → HR复核 → 面试 → 面试记录 → 最终决策

**一个关键点：不要把“抽取”和“评分”混在一起。**
否则以后换模型、修改评分规则、做招聘合规审计都会很麻烦。

如果你准备实际开发，我建议下一步直接把这些字段整理成一份 **「简历标准 JSON Schema（V1）」**，可以直接作为 **TextIn → Kimi → JEV** 三个环节之间的数据协议。


如果你的目标是做 **JD → 结构化 → 简历匹配 → JEV 判断**，JD 抽取不能只提取“岗位名称、学历、工作经验”。最好把 JD 拆成 **岗位基本信息、硬性要求、能力要求、职责、加分项、限制条件、评价规则**。

## 一、岗位基本信息

这是 JD 的“身份信息”：

| 字段   | 示例        |
| ---- | --------- |
| 岗位名称 | 海外产品质量工程师 |
| 岗位方向 | 产品质量      |
| 职能类别 | 质量/研发/工程  |
| 所属部门 | 海外事业部     |
| 职级   | 专员/主管/经理  |
| 招聘人数 | 3人        |
| 工作地点 | 上海/德国     |
| 汇报对象 | 海外质量总监    |
| 下属人数 | 0–5人      |
| 工作性质 | 全职        |
| 招聘类型 | 社招/校招     |
| 薪资范围 | 20–30K    |
| 到岗时间 | 1个月内      |

# 二、岗位核心职责

这是非常重要的一层，因为**候选人是否真正做过类似工作**，主要靠这里判断。

建议把每条职责拆成结构化信息：

```text
职责名称
职责描述
业务领域
工作对象
工作动作
工作成果
重要程度
```

例如：

> 负责欧洲市场产品质量问题闭环，推动跨部门解决客户反馈问题。

可以拆成：

```json
{
  "responsibility": "海外产品质量管理",
  "actions": [
    "质量问题分析",
    "客户反馈处理",
    "跨部门协调",
    "问题闭环"
  ],
  "business_area": "欧洲市场",
  "importance": "核心"
}
```

```text
是否接受应届生
```

> 本科及以上，车辆工程、机械工程相关专业。

```json
    "type": "相关专业",
    "majors": [
      "车辆工程",
```

# 四、工作年限要求

这里建议特别结构化：

```text

```

例如：

> 5年以上汽车行业工作经验，3年以上海外质量相关经验。

应该变成：

```json

    "min_years": 5
  },
  "industry_experience": {

  },
```

> 汽车行业 6 年 / 海外质量 2 年

# 十五、优先项 / 加分项

这个非常关键。

JD 中经常出现：

> 有海外工作经验者优先
> 有汽车行业经验者优先
> 有英语能力者优先

不能和硬性要求放在一起。

建议分成：

### 必须条件

```text
MUST
```

### 优选条件

```text
PREFERRED
```

### 加分条件

```text
BONUS
```

### 其他信息

```text
INFORMATIONAL
```

# 十六、最重要：把 JD 转成「招聘评价模型」

这是你的系统真正有价值的地方。

例如原始 JD：

> 本科及以上，车辆工程、机械工程相关专业；5年以上汽车行业经验，3年以上海外质量工作经验；英语可作为工作语言；熟悉8D、SPC等质量工具；有欧洲项目经验优先。

最终不要只保存成文本，而是变成：

```text
岗位：海外产品质量工程师
```

# 十七、再往前一步：给每个要求加「权重」

这样 JEV 才能真正做筛选。

例如：

| 要求      | 类型 |  权重 |
| ------- | -- | --: |
| 本科及以上   | 硬性 |  必须 |
| 汽车行业≥5年 | 硬性 |  必须 |
| 海外质量≥3年 | 核心 | 30% |
| 产品质量管理  | 核心 | 20% |
| 海外项目    | 核心 | 15% |
| 英语      | 核心 | 15% |
| 8D/SPC  | 专业 | 10% |
| 欧洲项目    | 加分 |  5% |
| 新能源汽车   | 加分 |  5% |

不过这里我建议**不要让 LLM 自己随便决定权重**。

最好是：

> **HR定义岗位评价模板 → Kimi抽取JD → JEV根据模板进行匹配。**

这样你的系统结果会稳定很多。

## 最终可以形成一个非常清晰的数据流

```text
                   JD
                    │
                    ▼
              ┌──────────┐
              │  TextIn   │
              │ 文档解析   │
              └────┬─────┘
                   │
                   ▼
              ┌──────────┐
              │   Kimi    │
              │ JD结构化   │
              └────┬─────┘
                   │
          ┌────────┴─────────┐
          ▼                  ▼
      JD事实层            JD评价层
   职责/学历/经验        MUST/PREFERRED
   技能/语言/项目        能力/权重/规则
          │                  │
          └────────┬─────────┘
                   ▼
             ┌──────────┐
             │   JEV     │
             │ 候选人匹配 │
             └────┬─────┘
                  ▼
       匹配结果 + 证据 + 缺口
```

**对于你的招聘 SaaS，我会把 JD Schema 设计成约 8 个一级模块：**

`岗位信息 → 职责 → 硬性条件 → 专业能力 → 通用能力 → 优选条件 → 工作条件 → 评价规则`

而简历则对应：

`候选人信息 → 教育 → 工作 → 项目 → 技能 → 证书 → 语言 → 成果`

这样 **JD Schema 和 Resume Schema 可以天然一一对应**，后面的 JEV 就能做结构化匹配，而不是拿两大段文本让模型“凭感觉打分”。
